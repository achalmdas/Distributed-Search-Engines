# Milestone 4 — Client integration contract (proposed)

**Scope:** `client/client.py` only; it does not implement or claim distributed election or distributed mutual exclusion on its own. The coordinator/gateway and each participating server node must supply those mechanisms. Do not claim full Milestone 4 compliance until the server components have been integrated and tested.

## Already implemented in the client patch

- A process-local, thread-safe **Lamport logical clock**. Every outgoing client request increments the counter and includes `sender_id` and integer `lamport_ts`. On receiving a reply, the counter becomes `max(local, reply.lamport_ts) + 1`; older gateways that omit timestamps still trigger a local receive increment. Logs include `CLOCK SEND` / `CLOCK RECEIVE`.
- Existing Milestone 1–3 commands still work (`--search`, `--update`, `--status`, `--p2p-search`, `--p2p-ring`, `--show-wire`). The M3 gateway currently accepts the two additional JSON keys, but it **drops them** when forwarding ordinary search requests and **does not return logical timestamps**. This must be fixed by the server team.
- `--coord-status`: reserved client request for elected leader and mutex information, **not supported by the M3 gateway yet**.
- `--demo-conflict DOC_ID`: launches two separate **client processes** concurrently to update the *same* document ID. Distinct ordered update IDs alone are **not proof** of distributed mutual exclusion; coordinator GRANT and RELEASE logs and a nonoverlap assertion are needed.
- `--gateway-host HOST` and `--gateway-port PORT` let the client address an alternate gateway endpoint if the team provides one.

## Wire contract to agree on with gateway/coordinator teammates

All messages remain one newline-terminated UTF-8 JSON object, as in Milestone 2.

A client update request:

```json
{"request_id":"<uuid>","msg_type":"update","doc":{"doc_id":16,"title":"Raft","body":"..."},"sender_id":"client-1234-abcd5678","lamport_ts":1}
```

**Every M4 receiver** should execute `C = max(C, incoming.lamport_ts) + 1`. **Every send** should execute `C += 1` and attach its current counter value. These are logical counters, **not** the existing UTC `ts` strings generated by `make_message`. A gateway must also keep a Lamport clock and preserve causal message metadata when it forwards work. Do not simply echo the received Lamport timestamp in a response.

Suggested new request:

```json
{"request_id":"<uuid>","msg_type":"coord_status","sender_id":"client-1234-abcd5678","lamport_ts":3}
```

Suggested gateway reply:

```json
{
  "request_id":"<same uuid>",
  "msg_type":"coord_status_result",
  "sender_id":"gateway-8000",
  "lamport_ts":14,
  "leader":{"id":"node-3","port":8033,"term":2},
  "mutex":{"resource":"document-index","owner":null,"queue_length":0},
  "nodes":[{"id":"node-2","lamport_ts":10},{"id":"node-3","lamport_ts":12}]
}
```

**The preceding response is an interface example, not actual output from the M3 repo.** The backend should register `coord_status` *before* its fallback-to-search branch in `gateway/gateway.py` (currently under `handle_client()`). It should return this request's `request_id`, live leader/lock state, and a **fresh response Lamport timestamp**. The UI tolerates missing optional fields, but `msg_type=coord_status_result` is required for success.

## Server-side tasks owned by other teammates

1. Give **each participating service process** its own Lamport counter (gateway, coordinator candidates, shards/replicas/peers participating in M4), with receive/send rules and readable logs. Decide whether the client also counts as a participating node in the report (it is timestamped here).
2. Implement a **real leader election** (e.g., Bully) among multiple *live candidate processes*, with leader announcement, failure detection, and replacement. Do not present restarting one singleton gateway as a distributed election.
3. Implement **centralized distributed mutual exclusion** (REQUEST → GRANT → RELEASE, with an explicit queue and distinct client/process IDs), or an alternative named in the assignment. A `threading.Lock` in a single process is not sufficient evidence. Protect the shared index-update resource and log wait/acquire/release times.
4. If a leader can crash while holding a grant, specify how a new leader reconstructs outstanding state and avoids simultaneously valid grants. An epoch/term plus **fencing token** checked by the actual update handler is a defensible design. If the team cannot guarantee recovery of the lock state, **fail closed** until recovered, not optimistically grant overlapping access.
5. The **client cannot rescue a dead gateway on port 8000** unless an alternate reachable address/routing or front-end failover exists; coordinate this before filming the leader-failure demonstration.
6. Ensure status/`update_result` replies carry `sender_id`, `lamport_ts`, and the existing `request_id`, without breaking Milestone 2 replication, shard catch-up, or Milestone 3 P2P behavior.

## Client verification add-on (Nov 12, 2026)

The enhanced client retains the original `--demo-conflict` command but strengthens its validation:

1. Two **separate client processes** send competing updates to the same document ID. Each child exports its **actual** `update_result` as a machine-readable JSON line for the parent (without changing gateway wire format).
2. The parent checks both actual responses, their distinct update IDs, `in_sync=True`, **3/3 index-shard ACKs**, **3/3 replica ACKs**, and agreement across replica digests for each response.
3. After both writers finish, the parent issues a separate **status** request and confirms every live shard and replica reports `next_update_id` above the higher of the two write IDs and that the three full replicas share the digest from the most recently ordered update.
4. The optional `--evidence-file logs/m4_conflict_evidence.json` stores the actual gateway responses and a per-check PASS/FAIL summary. The program returns nonzero if the checks fail.

This verifies **client-observed total order and replica agreement** and creates better report evidence. It still **cannot prove mutual exclusion**, because the existing gateway uses only a local `threading.Lock`. The actual distributed mutex protocol and proof of no overlapping GRANTs must be demonstrated on participating server nodes.

The new `--observe-leader 60` command provides a *read-only* observation and post-change search availability test for server-side leader election. It requires the gateway to implement the proposed `coord_status_result` response. It records two real observations with different nonempty leader IDs and verifies a search reply after the change. It does not trigger leader failure, elect a candidate, or prove that the server election algorithm is correct. If the M3 gateway is still in use, it fails immediately with a clear unsupported-status message.

Do not label the two `logs/*.json` files "mutual exclusion proof" or "election implementation." They are client-observed evidence to **pair with genuine leader-election and REQUEST/GRANT/RELEASE logs**. Running the conflict demo modifies document ID 16; use a known demo ID and avoid production data.

The client patch modifies only `client/client.py`, `tests/test_client_m4.py`, and client documentation. It does not change the server protocol or require any new Python packages.
